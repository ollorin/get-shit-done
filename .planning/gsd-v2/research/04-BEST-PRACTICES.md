## (a) Top 15 practices

Ordered by expected leverage on our measured cost/time. "Candidate" = for the Opus decision step.

### P1. Give long-lived coordinators a 1-hour prompt-cache TTL (subagents default to 5 min)
- **Claim.** Cache lifetime is per request bucket. Main conversation on a subscription (within plan usage) gets 1 h; everything else, explicitly including subagents and workflows, gets **5 min** unless set. Controls: `subagentPromptCacheTtl` setting / `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL=1h` (bucket "everything else"), per-agent `cacheTtl` under the `experimental` frontmatter field (v2.1.248+), `ENABLE_PROMPT_CACHING_1H=1` (both buckets). All need v2.1.242+; we are on 2.1.304. The doc says 1h writes are billed at a higher rate and are wasted on short bursts that never idle past 5 min.
- **Source.** https://code.claude.com/docs/en/prompt-caching ("Cache lifetime", "Which TTL each request gets", "Subagents and the cache"); https://code.claude.com/docs/en/best-practices (cost note: "Subagents get five minutes unless you change it"). **DOC.**
- **Applies to us.** This explains 01-F2 exactly: phase coordinators are subagents, so they sit in the 5-min bucket, and every poll after >=300 s re-wrote their context (325M of 333M cache-write tokens, ~$767 premium). Nothing in `~/.claude/settings.json` sets a TTL. A per-agent `experimental: cacheTtl: 1h` on `gsd-phase-coordinator` only (not on 3,900 short-lived helpers) targets the waste without paying the 1h write premium on helpers. Expected effect: polls spaced <60 min become cache reads (0.1x) instead of writes (1.25x); this is a config experiment that needs no redesign and can run before P2. Verify with `claude -p ... --output-format json` -> `usage.cache_creation.ephemeral_1h_input_tokens` and the existing `22_cache_all.py`.
- **Caveats.** 1h is ignored while the subscription is drawing usage credits (DOC). The 1h/5m write price ratio comes from the API pricing page (not re-fetched this run; I recall 2x vs 1.25x base input): confirm before computing the break-even. How cache tokens count against subscription limits (as opposed to our dollar index) is unverified.

### P2. Never poll with model turns; use one blocking call or a deterministic script
- **Claim.** (i) Subagents started from the main conversation are background by default; the parent gets a "completion notification in a later turn" and waits for it. In `-p`/SDK, Claude can wait. Interactive fork mode can be turned off (`CLAUDE_CODE_FORK_SUBAGENT=0`) so Claude waits for results. (ii) Background Bash gets 30 min by default, up to 2 h via `timeout`; foreground Bash caps at 10 min. A single background `until <condition>` command with `timeout` up to 7,200,000 ms ends in one notification = one model turn. (iii) Monitor streams stdout lines as events but each watch has a 5-min default, 30-min max deadline (10 min in `-p`). (iv) **Dynamic Workflows** (`Workflow` tool, JS script): "the script holds the loop, the branching, and the intermediate results itself, so Claude's context holds only the final answer"; resumable within a session; stalled agents auto-restart (<=5 retries); 16 concurrent agents default; 1,000 agents/run.
- **Source.** https://code.claude.com/docs/en/sub-agents (foreground vs background, "Let Claude wait"); https://code.claude.com/docs/en/tools-reference (Bash timeouts, Monitor); https://code.claude.com/docs/en/workflows. **DOC.**
- **Applies to us.** 01-F2 (3,883 sleep/until calls, 91% of coordinator active time) and 03 design notes. The 10-min foreground cap is the structural cause of the cache-miss polling in 01-F2. Candidate A: coordinators block on the child (foreground Agent call or one long background `until` with `timeout`). Candidate B: move the fan-out/wave loop into a Workflow script so no LLM loops at all (removes 03-F1/F4 by construction; `workflow-authoring` skill is installed here). Limits to design around: workflow scripts have no filesystem/shell access themselves, no `import()`, no mid-run user input (sign-off between stages = separate workflows).
- **Do not over-read.** No source shows a Workflow coordinating multi-hour, multi-plan phases with git side effects; that is unverified (see section c). A foreground wait still pays one parent cache re-write per child completion if the child outlasts the parent's TTL (prompt-caching doc: cache "expires after a period of inactivity"), so P1 and P2 are complements.

### P3. Shrink what every spawn inherits; scope the rest
- **Claim.** CLAUDE.md target is "under 200 lines per file; longer files consume more context and reduce adherence"; imports "don't reduce its context cost". Path-scoped rules (`paths:` frontmatter) load only when matching files are touched; rules without `paths:` load every session. Multi-step procedures and part-of-codebase rules belong in skills or path-scoped rules. Non-fork subagents load **all CLAUDE.md levels** by default; built-in Explore and Plan skip CLAUDE.md and git status; a custom subagent can set `omitClaudeMd: true` (skips user, project, local CLAUDE.md; managed policy still loads). `/doctor prompt-audit` audits instruction files; `/usage` flags rows like "Trim CLAUDE.md - 49k tokens per request".
- **Source.** https://code.claude.com/docs/en/memory ("Write effective instructions", "Organize rules"); https://code.claude.com/docs/en/sub-agents ("What loads at startup", frontmatter table). **DOC.** Independent support: Gloaguen et al., "Evaluating AGENTS.md", arXiv 2602.11988 (ICLR 2026): across Claude Code/Sonnet-4.5, Codex, Qwen Code, context files tended to lower task success and raised inference cost >20%; authors recommend minimal, non-inferable requirements only. https://arxiv.org/pdf/2602.11988 (via search summary; abstract figures vary by secondary source). **PAPER (summary only read).**
- **Applies to us.** 01-F6 (16k-token block in all 3,981 subagents, ~$474; whole startup context 15% of cost) and 01-hyp 3. Concrete levers: (a) `pre-pr-quality-gates.md` has no `paths:`, so it ships to every Haiku log-reader; scope it or move it into the `/gsd:open-pr` skill/hook path; (b) CLAUDE.md is 273 lines, over the documented 200; (c) put `omitClaudeMd: true` on helper-class agents that never need project policy; (d) route "read this log" helpers to built-in **Explore** (skips CLAUDE.md) instead of `general-purpose` (1,026 Haiku spawns, each carrying 16k+8.4k tokens of instructions and skill listing, 01 §2a). Expected: up to the ~$474 carrying cost for CLAUDE.md/MEMORY/rules plus part of the 8.4k skill listing.
- **Caveat/conflict.** See Q1 section: docs say auto memory is not loaded into subagents; this very subagent's transcript contains `MEMORY.md`, `CLAUDE.md`, `RTK.md` and `pre-pr-quality-gates.md` (checked in `.../subagents/agent-af6b7c5182458016f.jsonl`). Whether `omitClaudeMd` also removes rules and memory is unverified; probe first.

### P4. Put must-not-fail rules in hooks and deny rules, not in emphatic prose
- **Claim.** "CLAUDE.md is for guidelines, and Claude is allowed to decide a guideline doesn't apply. If something has to happen every time, make it a hook, a deny rule, or a managed setting." "If Claude keeps ignoring a line... adding IMPORTANT probably won't fix it. Either the file has grown long enough that the line gets lost, or the line is a rule that can't have exceptions." A `Stop` hook (exit 2) sends Claude back to work until a check passes (auto-overridden after 8 consecutive blocks). `prompt`/`agent` hooks are model-judged, not deterministic. Keep the enforced set small ("forty of them... most are probably preferences"). Also `SubagentStart`/`SubagentStop`/`TaskCompleted`/`SessionStart` events exist.
- **Source.** https://code.claude.com/docs/en/best-practices ("Enforce the rules that can't have exceptions", "Enforce the check with a Stop hook"); https://code.claude.com/docs/en/hooks-guide. **DOC.**
- **Applies to us.** CLAUDE.md carries ~12 MANDATORY/NEVER/MUST lines (preflight, `--no-verify`, fp gate, subagent tiers). Candidates: `Stop`/`SubagentStop` hook that refuses to end an executor turn without a SUMMARY.md/commit on disk (directly attacks 03-F1/invariant 1, "completed is never trusted alone"); `PreToolUse` deny for `git stash|reset|clean` on the shared branch (CLAUDE.md "Orchestration hard rules"). Whether `SubagentStop` can inject a model-visible reason for background agents: unverified (docs show `Stop`/`SubagentStop` "reason is fed back to Claude"; behaviour for background subagents not probed).

### P5. Drop ALL-CAPS/MUST emphasis; it now over-applies
- **Claim.** "Older models sometimes needed the emphasis. Current ones follow a plainly worded line, and piling on emphasis mostly makes Claude over-apply the rule." Prompting guide: for Opus 4.5+ "soften any aggressive language... Where you might have said 'CRITICAL: You MUST use this tool when...', use 'Use this tool when...'". Also: "Tell Claude to keep going, loop until done, don't be lazy" is "more likely to cause over-work than fix a stall"; "Tune anti-laziness prompting".
- **Source.** https://code.claude.com/docs/en/best-practices (table "Instead of... do this"); https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices (tool-use and migration sections). **DOC.** Upstream GSD did it: v1.37.0 (2026-04-17) "Trims emphasis markers in the top four agents" — https://raw.githubusercontent.com/glittercowboy/get-shit-done/main/CHANGELOG.md. **PRAC (changelog, no measurement).**
- **Applies to us.** Executor/verifier/coordinator definitions (counts above) and CLAUDE.md "Don't stop early or ask permission", "Zero tolerance" lines (these directly match the docs' "keep going" anti-pattern and may contribute to 01-F10 review churn and over-work; unmeasured). Cheapest experiment in S3: rewrite emphasis to plain statements in two agents, A/B on the same plans, compare turns and findings.

### P6. Fresh-context review with a bounded loop, and filter by severity in a separate pass
- **Claim.** A reviewer in fresh context helps because it has not seen the reasoning; "Handing the same task to a subagent doesn't make the answer any better." "A reviewer that's asked to find problems will always find something. If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen" — so tell it what to skip. Opus 5 guide: don't use "report only high-severity" in the reviewer prompt (it is followed literally); report everything and filter in a separate pass; and "do not use subagents to verify or double-check your own work". Sonnet 5.5 guide: at `max` effort, forbidding self-launched reviewer subagents cut session cost ~1/3 "with no change in quality" (Anthropic test). Huang et al. (ICLR 2024): intrinsic self-correction without external feedback does not reliably improve reasoning and can degrade it; it helps style/safety.
- **Source.** https://code.claude.com/docs/en/best-practices (review section; table); https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5 ("Code review", "Controlling subagent spawning"); https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5 ("Thoroughness at xhigh and max"); https://arxiv.org/abs/2310.01798 (Oct 2023). **DOC + PAPER.**
- **Applies to us.** 01-F9/F10: review ~16-18% of cost; 78% of Sonnet reviews end with findings, 67% of 860 findings LOW; rounds "to zero findings" is by construction unbounded when the reviewer always finds something. Candidate: reviewer outputs a severity-tagged list (schema), loop exits on "no finding >= MED" or a round cap, LOW logged not fixed; deterministic gates (tests, types, fp-gate) are the termination criterion, not reviewer silence. This conflicts with the CLAUDE.md policy "fix review findings of every severity", so it is a policy decision, flagged for Opus. No source found that quantifies the payoff of N rounds (see c).

### P7. Cap delegation: depth, concurrency, and "don't delegate what you can do in a few calls"
- **Claim.** Anthropic's own multi-agent research system: ~4x tokens vs chat for agents, ~15x for multi-agent; token usage alone explained 80% of BrowseComp variance; good fit is breadth-first parallel work, poor fit is "domains that require all agents to share the same context or involve many dependencies" and "most coding tasks have fewer truly parallelizable pieces". Early failure: 50 subagents for a simple query; fix was effort-scaling rules in the prompt (1 agent/3-10 calls for simple, 2-4 subagents for comparisons). Claude Code docs: a fresh subagent "can end up slower than doing the task where you are"; defaults are depth 3 below main (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`), 20 concurrent (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`). Opus 5 "delegates to subagents more readily than prior models", so cap deterministically.
- **Source.** https://www.anthropic.com/engineering/built-multi-agent-research-system; https://code.claude.com/docs/en/best-practices ("Know what subagents cost"); https://code.claude.com/docs/en/sub-agents ("Nesting"); Opus 5 guide above. **ENG + DOC.**
- **Applies to us.** 01 §0: depth 1/2/3 = 451/2,097/1,435 spawns (we sit at the default depth limit), coordinator->general-purpose 611, executor->general-purpose 1,012, 38/91 coordinators were resumes. A research system where subagents search is not our setting (dependent coding pipeline), so the 15x figure is an upper-bound warning, not a measured analogue. Candidate: depth cap 2, an explicit delegation rule in the executor/coordinator definition, `maxTurns` on helpers.

### P8. Prompt per model tier: stop/verify paragraphs for Haiku/Sonnet, remove verify instructions for Opus, set effort explicitly
- **Claim.** Haiku 5.5: "With a long coding-agent system prompt at `low` effort, it sometimes stops early and hands the task back"; at low/medium it "sometimes reports a code change as done without running a check"; moving low->medium roughly halved early stopping but more than doubled output tokens per attempt. Anthropic supplies two paragraphs to add (keep working until done; run a real check before reporting done). `medium` is the default. Sonnet 5.5 has the same two behaviours at low/medium. Opus 5: "Claude Opus 5 verifies its own work without being told... remove [explicit verification instructions]; they cause over-verification". `effort` is a subagent frontmatter field; for Haiku/Sonnet 5.5 an effort change keeps the cache by default.
- **Source.** https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5; .../prompting-claude-sonnet-5-5; .../prompting-claude-opus-5; https://code.claude.com/docs/en/sub-agents (frontmatter `effort`). **DOC.**
- **Applies to us.** 01-F14 (Haiku executor $0.67/spawn, 509 spawns; Sonnet $3.27) and the "long system prompt" condition: our Haiku executor starts with a 12.4k-token agent definition plus 15.9k tokens of inherited policy (01 §2a). Candidates: add the two Anthropic paragraphs to gsd-executor (Haiku/Sonnet) and delete "final verification" boilerplate from Opus-run roles (planner, plan-checker, verifier); pin `effort: medium` for Haiku executors; measure early-stop rate (01 finding 11: 128 transcripts end on API error, separate issue).

### P9. Risk-proportional proof: mutation testing where a surviving mutant is costly, coverage elsewhere
- **Claim.** Meta's ACH (FSE 2025 industry): LLM-generated mutants plus LLM test generation; engineers accepted 73% of generated tests; 277 of 571 useful tests "would have been discarded had the team focused solely on line coverage"; equivalent-mutant agent precision/recall 0.79/0.47, rising to 0.95/0.96 with simple preprocessing (a real cost driver: equivalent mutants). Mutation score is argued to be a more meaningful adequacy metric than coverage. Anthropic's own guidance ties verification to cheap, deterministic checks (tests, typecheck, Stop hook) and asks for evidence (command + output), not "all tests pass".
- **Source.** https://arxiv.org/html/2501.12862v1 (Jan 2025; via search summary); https://code.claude.com/docs/en/best-practices ("Give Claude a check to run"). **PAPER + DOC.**
- **Applies to us.** DECISIONS 2026-10-31 already allows relaxing proof policy; review+rulings ~26% of cost. Evidence supports using mutation proof where the oracle is weak and the blast radius high (money/auth/KYC, already the P0 tier) and not as a universal gate. No source measures mutation-testing cost for LLM-written TypeScript/Deno code, so cost/benefit for us must be measured (S3 experiment).

### P10. Keep orchestration state on disk, one unit per session, verify before trusting "done"
- **Claim.** Anthropic's long-running-agent harness: initializer + coding agents with `init.sh`, a progress file, git commits as checkpoints, a JSON feature list (JSON chosen because models alter it less than Markdown; agents may flip only `passes`), one feature per session, a startup routine (read progress, run a smoke test), browser e2e testing. Failure modes they report: declaring victory too early, marking features done prematurely, leaving the environment broken. Prompting guide: JSON for structured state, free text for progress notes, git for checkpoints; "Claude's latest models perform especially well in using git to track state". Upstream GSD 1.42.0 added executor stall detection + safe-resume and a verifier that runs probe scripts "rather than trusting SUMMARY markers".
- **Source.** https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents; https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices ("Long-horizon reasoning and state tracking"); upstream CHANGELOG (link in P5). **ENG + DOC + PRAC.**
- **Applies to us.** 03 invariants 1-4, TASK-CHECKPOINT.json, 01-F11 (42% of coordinator spawns are resumes; phase 400 had 26). Independent confirmation of the on-disk-truth rule we already follow; the new element is making resume cheap: a small machine-readable task list (JSON) + commit trail as the only resume input, not the full coordinator history.

### P11. Protect the prompt-cache prefix in every long-lived agent
- **Claim.** The cache is exact-prefix. Invalidators: model switch (each model has its own cache, including skill/command frontmatter `model:` and `opusplan`), effort change on older models, fast mode, adding/removing tool definitions or deferring-less MCP servers, compaction (conversation layer), accumulating images (oldest images dropped in batches -> reprocess), Claude Code upgrade. Cache-safe: editing CLAUDE.md mid-session (does not apply either), skills/plugins/agents appended as messages, permission mode, `/rewind`. Order: system prompt -> project context (CLAUDE.md, memory, unscoped rules) -> conversation. `/usage` shows a `Prompt cache (main)` line with hit ratio and "likely cause" of the last miss; idle compaction compacts >200k-token sessions on the 1h TTL shortly before expiry.
- **Source.** https://code.claude.com/docs/en/prompt-caching (whole page, incl. "Actions that invalidate the cache", "Check cache performance"); design rationale: https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything (linked from the doc; **not fetched** — 308 redirect to claude.dev not followed). **DOC.**
- **Applies to us.** 01-F1 (cache = 85% of cost). Our workflows launch agents with different models per tier (fine, separate sessions) but any single agent that switches model/effort mid-run pays full re-write; screenshot-heavy Charlotte runs hit the image-batch drop. Resumed coordinators (38/91) re-pay the whole prefix: resume-with-small-brief beats `SendMessage` into a stale session whose cache is cold.

### P12. Plan for weekly limits explicitly; Workflow auto-continue does not cover them
- **Claim.** Interactive subscription sessions wait and auto-continue after a usage limit (v2.1.234+), but only if the reset is within 24 h, and re-arm at most twice in a row. Workflows pause (rather than fail) on a limit and resume ("requires 2.1.271+"), but only in interactive subscription sessions: not `claude -p`, SDK, background sessions, Remote Control or agent-team teammates; "A weekly limit can reset further out" and then the agent fails. SDK has `max_budget_usd`/`--max-budget-usd` and `--output-format json` returns `total_cost_usd`; `/usage` attributes usage by skill/subagent/plugin/MCP.
- **Source.** https://code.claude.com/docs/en/interactive-mode ("Wait for a usage limit to reset"); https://code.claude.com/docs/en/workflows ("When a run hits your usage limit"); https://code.claude.com/docs/en/headless; https://code.claude.com/docs/en/costs. **DOC.**
- **Applies to us.** 01-F3: the two stalls were ~52 h and ~84 h weekly resets, beyond the 24-h auto-wait window, so neither native feature would have saved them. Net: a budget governor (README S-hyp 5) remains the only lever; native tooling gives measurement (`/usage` attribution, `total_cost_usd`), not a weekly-limit API. No documented programmatic read of remaining weekly quota was found (unverified). Opus is 31% of est. $ (01-F9), so Opus routing is the biggest controllable share.

### P13. Skills + scripts for procedures (progressive disclosure), small descriptions, scripts executed not read
- **Claim.** Skill metadata is preloaded; the body loads when relevant; linked files load on demand; keep SKILL.md <500 lines; references one level deep; description+when_to_use truncated at 1,536 chars in the listing; "scripts can run as tools without being loaded into context"; prefer pre-made scripts over generated code (reliable, token-free, consistent). Test skills on Haiku, Sonnet and Opus ("What works perfectly for Opus might need more detail for Haiku"). `disable-model-invocation: true` stops auto-loading and preloading into subagents. Subagent `skills:` preloads full skill content. Upstream GSD cut cold-start prompt overhead ~2,150 -> ~120 tokens with namespace routers (1.41.0), capped skill descriptions at 100 chars with a lint gate, merged 86 -> 59 skills, added size-budget tests per agent (1.37.0: XL 1600 / LARGE 1000 / DEFAULT 500 lines).
- **Source.** https://code.claude.com/docs/en/skills; https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices; https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills; upstream CHANGELOG. **DOC + ENG + PRAC.**
- **Applies to us.** 01-F7 (<=2% of agents read any `~/.claude/get-shit-done/**` file; load is dominated by agent definitions, 7-36k chars) and 01-hyp 4 (bookkeeping to scripts: 13% of output tokens writes `.planning`/evidence docs). gsd-plan-checker.md is 33.9 KB, gsd-executor.md 30.7 KB, gsd-verifier 21 KB; our fork is 1.18.0 and predates upstream's agent size budgets. The 8.4k-token skill listing in each general-purpose spawn is a separate lever (whether `disable-model-invocation` removes entries from the listing: unverified).

### P14. Browser QA: prefer ref-addressed snapshots/targeted finds over screenshots; avoid image accumulation; measure
- **Claim.** Playwright MCP docs: snapshot token cost "Low - text only", screenshot "High - image tokens"; refs `eN` valid until the page changes; reduce with `browser_snapshot` `target`/`depth`/`filename`, `--snapshot-mode=none`, and `browser_find` ("far cheaper" than a full snapshot on large pages); use screenshots in addition when visuals matter (canvas, charts). Claude Code drops oldest images in batches once image limits are hit (one cache re-read per batch). Anthropic's harness blog: Puppeteer e2e caught bugs code inspection missed; native alert modals are a blind spot. Third-party reports: CLI-driven tools (Playwright CLI, Vercel agent-browser) avoid MCP tool-schema overhead and cost 4x or more less than Playwright MCP (single-source figures: 114k vs 27k tokens/task; 7,779 vs 1,364 for a six-step test; MCP fixed overhead ~13.7k tokens) — **VENDOR/PRAC, directional only**; sources disagree on snapshot vs screenshot size (200-400 vs ~10,220 tokens for a full a11y snapshot vs ~1,866 for a viewport screenshot).
- **Source.** https://playwright.dev/mcp/snapshots; https://code.claude.com/docs/en/prompt-caching ("Accumulating many images"); https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents; third-party roundups surfaced by search (itnext.io "Why does Playwright MCP use so many tokens?", morphllm.com/playwright-mcp, nikiforovall.blog 2026-07-05). **DOC/ENG + VENDOR.**
- **Applies to us.** 01-F4: 68% of Charlotte wall time is one broken call (`Page.captureScreenshot` 180 s timeout) — a defect to fix before any practice applies. After that: Charlotte `observe`/`find` (structured) before `screenshot`; Haiku runners already used. DECISIONS keeps UI tests LLM-driven; the evidence here is about token/turn cost per step, not about replacing the LLM. No source found on LLM-driven UI test speed practices beyond fewer, larger steps (see Q7).

### P15. Keep the always-loaded memory a short curated index; do not let agents grow it unreviewed
- **Claim.** Auto memory: first 200 lines or 25 KB of MEMORY.md load every session; Claude Code nags when near the limit ("one line per entry, move detail into topic files, merge or drop stale entries"). "If two instructions contradict each other, Claude may pick one arbitrarily." Anthropic context-engineering post: structured note-taking outside the window, just-in-time retrieval of references, compaction; context is "a finite resource with diminishing marginal returns" (context rot). AGENTS.md study: agent-written context files do not help on average and cost more; human-written ones give small gains, mainly for non-inferable conventions.
- **Source.** https://code.claude.com/docs/en/memory ("Auto memory", "Troubleshoot"); https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents; https://arxiv.org/pdf/2602.11988. **DOC + ENG + PAPER (summary only).**
- **Applies to us.** MEMORY.md is 14.1 KB / 74 long lines (under the 25 KB cap but ~16k tokens of the inherited block with CLAUDE.md + rules); entries are agent-authored, include incident narratives, and several restate CLAUDE.md rules (e.g. Haiku/Sonnet/Opus tiering, fix-all-findings), which is the contradiction/duplication risk the docs warn about. Candidate: index lines <=150 chars, topics loaded on demand, subagent-class agents get a role-specific excerpt or none.

## (b) Findings by question

### Q1. Instruction size and structure; what subagents inherit

**Findings**
- Official size guidance: CLAUDE.md under 200 lines/file; MEMORY.md loads only the first 200 lines or 25 KB; subdirectory CLAUDE.md and path-scoped rules have a smaller per-file limit and are truncated with a "read the rest" note; CLAUDE.md up to 4 MiB loads whole. Sources: https://code.claude.com/docs/en/memory. DOC.
- Placement taxonomy (docs): CLAUDE.md = facts needed every session that Claude cannot infer; path-scoped rules = part-of-codebase rules; skills = procedures loaded on demand ("A long release procedure sitting in a skill doesn't [cost context]"); hooks/deny rules = anything that cannot have exceptions; on-demand docs = referenced paths. Same rule applies to skills: "only write down what Claude can't find on its own." https://code.claude.com/docs/en/best-practices. DOC.
- Emphasis: see P5. Anthropic's own skill-authoring doc still shows "ALWAYS use this exact template" and "MUST filter" for strict outputs (https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); the reconcilable reading is emphasis only for true low-freedom invariants, and prefer a hook when enforcement matters.
- Subagent inheritance (DOC, https://code.claude.com/docs/en/sub-agents "What loads at startup"): fresh context; system prompt = the agent's markdown body plus env details (not the Claude Code system prompt); task message; **all CLAUDE.md levels** (Explore/Plan skip; `omitClaudeMd: true` skips user/project/local); git status snapshot (not Explore/Plan); only the skills in `skills:`; sibling roster if SendMessage; tools inherited and narrowed; background subagents get a smaller tool set. Not inherited: conversation history, output style, and (per docs) the main conversation's auto memory. Forks inherit the parent's full context/system prompt and read the parent's cache.
- Claude Code best-practice page on over-prescription: "Describe your architecture and file layout in CLAUDE.md -> Claude reads the repo itself. Only write down what isn't in there."
- Anthropic "right altitude" (ENG): prompts should avoid both brittle hard-coded logic and vague guidance; minimal viable tool set. https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents.
- Empirical: AGENTS.md study (P3). Long-context degradation ("context rot", Chroma 2025; lost-in-the-middle) is repeatedly cited but I only reached secondary summaries; replication of position effects is mixed.

**Conflicts**
- **Docs vs observed behaviour on memory.** Docs: "The main conversation's auto memory isn't loaded into subagents" (https://code.claude.com/docs/en/memory). Observed: this subagent's transcript contains MEMORY.md, and 01 §2a measured it in subagents at ~12.5k chars median over 3,793 spawns. Possible explanations (all unverified): version difference, MEMORY.md injected by the project/user harness rather than auto-memory, or agent type differences. Probe: add an `InstructionsLoaded` hook (documented, logs which memory/rule files load and why) and spawn one `general-purpose`, one custom agent with `omitClaudeMd: true`, and one Explore.
- Skills doc's strict-template CAPS vs the "no emphasis" guidance (above).

**Not settled by sources:** the right size for an agent-definition file. Upstream chose line budgets (500/1000/1600); Anthropic gives 500 lines for a SKILL.md body and no number for subagent system prompts.

### Q2. Multi-agent orchestration; waiting without polling; recovery

**Findings**
- When it helps/hurts: P7. Claude Code docs add that subagents are for verbose side tasks, tool restriction, and self-contained work returning a summary; the main conversation is better when phases share significant context or latency matters. https://code.claude.com/docs/en/sub-agents "When to use subagents". DOC.
- Hierarchy depth: default max depth 3 below main, withheld `Agent` tool at the limit; 20 concurrent. Anthropic's research system used one lead + 3-5 parallel subagents; subagents wrote outputs to external storage and passed references back "to avoid game of telephone". ENG.
- Context size: workflow scripts keep intermediates in variables so the orchestrating context holds only the result; subagents return condensed summaries (1-2k tokens typical, context-engineering post); `agents write to disk, return references` (research system). Our coordinator contexts average 4.3M tokens/spawn processed (01 §1), i.e. long histories re-read per poll.
- Waiting primitives, with documented limits: see P2. Additional: `claude -p` waits for background subagents/workflows/Monitor/background commands at exit (10-min idle ceiling for some kinds; `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`), SIGTERM leaves the turn unfinished and `--resume` continues (`CLAUDE_CODE_RESUME_INTERRUPTED_TURN=1` continues the interrupted turn). https://code.claude.com/docs/en/headless. DOC.
- Programmatic orchestration from code: `claude -p --output-format json|stream-json` (cost + session_id per call, `--resume`, `--json-schema`, `--max-budget-usd`, `--bare` for reproducible runs but needs an API key, not the subscription login, and disables background tasks). Hence an OS-level driver (like `session-supervisor.sh`) can orchestrate `-p` runs on a subscription only without `--bare`. DOC.
- Crash/limit recovery: workflows replay completed agents from saved results; a failed agent re-runs and so does every later agent in the script (documented sharp edge); stalled agents restart with no transcript (files changed stay changed); agent-level `stallMs`/`CLAUDE_ASYNC_AGENT_STALL_TIMEOUT_MS`. Anthropic research system: resume from the point of failure using checkpoints. https://code.claude.com/docs/en/workflows; https://www.anthropic.com/engineering/built-multi-agent-research-system. DOC + ENG. Session-limit death of all agents (03-F3) has no native recovery beyond P12's 24-h window.
- Opus 5 is described as coordinating subagent teams well, "effective writer-verifier patterns and few cases of agents overwriting each other's work" (DOC), yet cap spawning for cost.
- Agent teams (experimental, `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`) cost ~7x tokens in plan mode (https://code.claude.com/docs/en/costs); not recommended for us.

**Conflicts**
- Anthropic research blog: multi-agent beat single-agent Opus by 90.2% on its research eval, versus Claude Code docs: delegating the same task to a subagent does not improve the answer and may be slower. Reconciliation: the gain came from breadth-parallel search, not from delegation per se; our pipeline is dependency-heavy coding, which the same blog says is the weak case.
- Workflows (code owns the loop) vs "find the simplest solution possible, only increase complexity when measured results show it helps" (https://www.anthropic.com/engineering/building-effective-agents, undated; notes the tooling landscape changed since Dec 2024). Both favor deterministic control flow where the path is known; the 03 doc's goal is that.

### Q3. Prompt-caching economics in Claude Code

- TTL answer: **1 h is available on a subscription, but only for the main conversation by default**; subagents/workflows/forks/compaction/titles are 5 min unless `subagentPromptCacheTtl`/`CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL`, per-agent `experimental.cacheTtl`, or `ENABLE_PROMPT_CACHING_1H=1`. `FORCE_PROMPT_CACHING_5M=1` overrides everything. Precedence list in the doc. Dropped to 5 min for the main conversation when the subscription spills into usage credits; set `promptCacheTtl` to keep 1h there. https://code.claude.com/docs/en/prompt-caching. DOC.
- Verify empirically: `claude -p "hello" --output-format json` and read `usage.cache_creation.ephemeral_1h_input_tokens` vs `ephemeral_5m_input_tokens`; `/usage` "Prompt cache (main)" line shows TTL in effect and warm/cold.
- Hit mechanics: exact-prefix, per model, per speed; cross-session sharing only if same directory and identical git-status snapshot; parallel sessions in the same directory can read each other's cache; resumed subagents can read the cache the original run warmed; a fork reads the parent's cache; Workflow fan-outs hold siblings up to 5 s (`CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS`) so they share a prefix. A normal subagent's first request does **not** read the parent's cache (different system prompt/tools).
- Long-running agent structure that minimizes re-writes (derived from the doc, not a single quoted rule): keep tool definitions and model fixed for the life of the agent; keep static instructions first (they are, by design); do not toggle MCP/plugins; avoid unnecessary images; compact at natural breaks; for idle-heavy agents choose 1h; cap polling gaps below the TTL; prefer resuming an agent whose cache is still warm over starting a fresh coordinator with a long brief only if the gap < TTL.
- Cost context: https://code.claude.com/docs/en/costs — "Cache misses: your first message after a break longer than the cache lifetime misses the cache and reprocesses your full context"; scheduled tasks, cross-session messages, goal check-ins and subagent requests each keep sending full context while you are idle (relevant to our wake-by-notification design: every wake sends full context).
- Subscription-limit accounting for cache tokens is not documented in what I read (see c).
- Conflict: none between sources; the only tension is our own index (cache-write 1.25x) vs the doc's "higher rate" for 1h writes; the break-even depends on the 1h write multiplier.

### Q4. Verification/QA evidence

- Review loops: no source quantifies the optimal number of rounds. What exists: fresh-context reviewer helps; reviewers always find something (DOC); self-review/self-refine without external signal is unreliable for reasoning (Huang et al., ICLR 2024; secondary summary of limits: a critic notes it tests only reasoning/knowledge tasks); multi-agent debate no better than self-consistency at equal sample count (same paper). Superpowers' two-stage (spec compliance, then code quality) review loop is described by third-party mirrors; I found no published results that it improves outcomes and a security vendor flagged "approval fatigue" risk. PRAC/unverified.
- LLM-as-reviewer reliability: Opus 5 doc claims high precision/recall on real bugs and "additional findings are mostly real issues" (Anthropic-authored, unaudited); Anthropic's research system found a single LLM-judge prompt (0-1 score + pass/fail) aligned best with humans but human testing still caught edge cases. No independent reliability study retrieved. Self-preference bias in LLM judges: search returned nothing; unverified.
- Mutation testing: P9. Additional: Wang et al. (TOSEM 2025, arXiv 2406.09843) LLM-generated mutants are more diverse and closer to real bugs than traditional tools, with higher non-compilable/duplicate/equivalent rates; MUTGEN (arXiv 2506.02954) feeds surviving mutants into test generation; Cabral et al. (SBQS 2025) compared GPT-4o vs DeepSeek unit tests via mutation. I did not retrieve numbers for the last two. PAPER (search summaries).
- Risk-proportional verification: Anthropic's guidance is to match checks to cost of failure and prefer deterministic checks first (tests, typecheck, Stop hook), with evidence requests rather than assertions; `/verify` builds and runs the app; plan-validate-execute with a script-validated intermediate file for batch/destructive operations (skill best-practices doc). DOC.
- Test-first with agents: Claude Code workflow "explore, plan, code" and "write a SPEC.md, build in a fresh session, review against the spec" (best-practices); Anthropic harness: failing JSON feature list defined up front, agents may not edit tests ("unacceptable to remove or edit tests"); prompting guide: do not hard-code to pass tests, report bad tests instead (https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices, "tests" snippet). DOC + ENG. No quantitative TDD-with-agents study retrieved.
- Practical conflict: Opus 5 doc says remove explicit verification instructions and verifier subagents (over-verification); Haiku/Sonnet 5.5 docs say add them at low/medium effort. Resolution is per-model prompts (P8). Our CLAUDE.md applies one policy to all tiers.

### Q5. Model routing

- Anthropic's stated roles: Sonnet for routine work and most coding; Opus for hard architecture/multi-step reasoning; "Haiku is a good fit for subagents doing simple jobs" (best-practices, costs). Opus 5 "performs best when given the complete task specification up front and left to run"; for the hardest long-horizon work "an Opus model is the better choice" than Sonnet 5.5. DOC.
- Reported small-model failure modes (Anthropic, Haiku 5.5): early stop and hand-back in long agent prompts at low effort; claims done without running a check at low/medium; searches/tools skipped with thinking off + JSON; system-prompt adherence weaker than at high effort. Fixes and measured effects are in P8. https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5. DOC.
- Plan granularity for small models: Skill-authoring doc: low-freedom (exact commands, "do not modify the command") for fragile steps; high-freedom for judgment steps; "what works for Opus might need more detail for Haiku". Anthropic's effort-scaling lesson (research system): put explicit scaling rules in the prompt because subagents cannot judge effort. Independent evidence: none retrieved. A search for controlled Haiku-vs-Sonnet plan-execution results found only anecdotal posts (a Portuguese blog citing 73.3% SWE-bench Verified for Haiku 4.5, unverified) and benchmark papers (SWE-Bench Pro, SWE-Marathon: 73% of agent failures are implementation failures/timeouts). So 01-F14's "no quality adjustment possible" stands; an A/B on identical plans is the only way to settle Haiku vs Sonnet executor.
- Mechanics: model resolution order per invocation > frontmatter > `CLAUDE_CODE_SUBAGENT_MODEL` > parent; `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` forces one model for all subagents/workflow agents (useful as a budget-governor lever). Cache is per model, so cross-model handoffs never share cache.

### Q6. Knowledge/memory across sessions

- Works (Anthropic): CLAUDE.md for rules; auto memory with a concise index and topic files, hard-capped at 200 lines/25 KB at load; structured note-taking (to-do/NOTES.md); progress file + git log + JSON test/feature list across context windows; just-in-time retrieval of file paths/queries instead of preloading; subagent-owned memory directories (`memory:` field) so a role accumulates its own notes. Sources: P10, P15, https://code.claude.com/docs/en/sub-agents (memory field). DOC + ENG.
- Reported to fail/hurt: agent-written or over-long context files raise cost >20% and slightly lower success (AGENTS.md study; PAPER, summary); contradictory instructions are picked arbitrarily (DOC); instructions given only in conversation disappear at compaction (DOC); stale entries; truncated overflow beyond the load cap (DOC). Retrieval/knowledge-base systems: I found no evidence-backed comparison; our own `gsd-meta-answerer`/knowledge DB agent never ran (01-F12), so there is no local evidence either.
- Use `SessionStart` with `compact` matcher to re-inject critical context after compaction (hooks guide). DOC.

### Q7. Browser QA agents

- Token patterns: P14. Prompting-guide hint for tool-heavy loops: Claude can call tools in parallel ("about 100 percent" success when prompted); batch independent calls per turn (https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices, "Optimize parallel tool calling"). DOC.
- Tool-description cost: MCP tool definitions are deferred by default in Claude Code (names only enter context), so the "MCP schema overhead" figures quoted by third parties (13.7k Playwright MCP, ~17k Chrome DevTools MCP) may not apply to Claude Code with tool search on; unverified for our Charlotte MCP. https://code.claude.com/docs/en/costs ("Reduce MCP server overhead"). DOC vs PRAC.
- Tool-output design: Anthropic "Writing tools for agents": cap responses (Claude Code default 25,000 tokens), pagination/filters, a concise-vs-detailed `response_format` (72 vs 206 tokens in their Slack example, about 1/3 the tokens), actionable error messages. https://www.anthropic.com/engineering/writing-tools-for-agents. ENG. Directly relevant to Charlotte `observe`/`diff` outputs.
- Speed: nothing authoritative found on LLM-driven UI test speed beyond fewer round trips and removing broken waits. Our dominant cost (01-F4, 180 s screenshot timeout on 95% of calls) is a defect.
- Pitfall: native browser dialogs were a blind spot for Puppeteer MCP in Anthropic's harness (ENG); Charlotte has `charlotte_dialog`.
