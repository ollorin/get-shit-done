# Deferred Items — Phase 44 (Reliability Foundations)

- [DEFERRED] `.planning/STATE.md`'s "Current Position" / "Progress" sections use a legacy format (`Plan: X of Y in current phase`, `Progress: [bar] N%`) that predates the `gsd-tools.js state advance-plan` / `state update-progress` CLI commands' expected schema (`Current Plan:` / `Total Plans in Phase:` literal fields, `**Progress:**` bold-markdown field). Both commands failed to parse/update STATE.md during 44-01 execution and STATE.md had to be updated manually instead. This is a pre-existing STATE.md/tooling schema mismatch, not something introduced by 44-01 — found during 44-01's state_updates step. Recommend a future plan (or a `gsd-tools.js state migrate` command) to bring STATE.md's Current Position section in line with the schema the CLI helpers expect, so `state advance-plan`/`state update-progress` work for all future plans without manual intervention.

- [DEFERRED] **Genuine cross-process concurrent `state update` (and other STATE.md/ROADMAP.md/config.json read-modify-write) calls can silently drop one writer's update.** Found during 44-05's integration test-writing (confirmed via 30/30 raw trials of two genuinely-simultaneous `state update` subprocesses racing on the same STATE.md). Root cause: `cmdStateUpdate` (and the other read-modify-write command handlers) does `fs.readFileSync` the whole file, mutates one field in memory, then calls `atomicWriteFileSync`. `atomicWriteFileSync` (44-02) only guarantees each individual write is complete-or-absent (no torn/corrupted file) — it does NOT provide cross-process locking, by explicit design (see 44-CONTEXT.md's 44-02 decision section: "Do NOT attempt true cross-process locking (mutex/semaphore) in this phase... sequential coordinator calls, not truly concurrent writers in the common case"). Under genuine concurrency, whichever process's write lands second overwrites the first process's field change with its own stale copy of the rest of the file. This is NOT a torn write (the file is always valid, readable Markdown) — it's a lost-update race. Sequential/rapid-succession writes (the pattern GSD's coordinators actually use — one coordinator at a time per phase, not simultaneous writers) are unaffected and fully covered by both 44-02's and 44-05's tests. Recommend: if a future phase ever introduces genuinely parallel coordinators writing to the SAME STATE.md/ROADMAP.md/config.json at the same time (not just parallel-eligible phases operating on separate phase directories), add real cross-process locking — `proper-lockfile` is already a vendored dependency reserved for Phase 47's Telegram JSONL hardening and could be reused here. Until then, this is an accepted, documented limitation, not a bug to fix in Phase 44 (test added to prove the ACTUAL current behavior — no crash, no corruption, but a possible dropped update — in `get-shit-done/bin/gsd-tools.test.js`'s "concurrent `state update` subprocesses racing on the same STATE.md (Phase 44-05)" describe block).
