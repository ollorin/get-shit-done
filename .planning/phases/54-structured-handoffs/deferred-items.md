- [DEFERRED] `cmdRoadmapGetPhase` (`roadmap get-phase` CLI command in gsd-tools.js) hardcodes a 3-hash `###\s*Phase` regex for both its start-header match and its next-header boundary match. The live `.planning/ROADMAP.md` actually uses 4-hash `#### Phase N:` headers throughout (confirmed by grep). Because the regex has no anchor, the 3-hash pattern still partial-matches inside the 4-hash header (skipping the leading `#`), but the next-header boundary regex (`\n###\s+Phase\s+\d`, which requires whitespace immediately after exactly 3 hashes) never matches a `\n####` header, so `roadmap get-phase <N>` currently returns the phase's section running all the way to EOF (through every later phase and the Progress table) instead of stopping at the next phase heading — found during 54-02's execution while building `getPhaseInvariantsText`, which was designed to reuse this exact slice logic per the plan's instruction. Out of scope for 54-02 (fixing `cmdRoadmapGetPhase` itself was not this plan's task; `getPhaseInvariantsText` was written with its own hash-run-capture fix instead so it does not inherit the bug). Should be fixed by applying the same `(#{2,6})` capture-and-reuse approach to `cmdRoadmapGetPhase`, with a regression test against a ROADMAP.md fixture using 4-hash headers.
