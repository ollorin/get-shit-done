## Phase Boundary

The escalation channel every other autonomy feature routes through is reliable for unattended runs — daemon death is detected instead of silently hanging, state files can't corrupt, delivery failures are detected and retried, and a blocking question that goes unanswered overnight resolves to a defined fallback instead of hanging the run.

## What the Audit Doc Got Right, and Where It Drifted (verified against current source, 2026-07-04)

**Confirmed still true:**
- `question-service.ts` `saveState()` (line ~413) uses bare `fs.writeFileSync()`, no locking, no atomicity. `proper-lockfile` is a dependency (`package.json`) but never imported anywhere in `src/`.
- State file path is hardcoded and NOT project-scoped: `path.join(os.homedir(), '.claude', 'knowledge', 'question-state.jsonl')` — shared across every GSD project on the machine.
- IPC socket path IS already project-scoped (`shared/socket-path.ts`, SHA1(projectRoot).slice(0,8)) — this part of the audit's "no locking" section correctly separates the (fine) socket-path story from the (broken) state-file-path story; don't conflate them.
- No `ping`/health-check IPC method exists.
- Voice transcription failure (`whisper.ts`) returns an error string instead of throwing; `handlers.ts` correctly detects the `[Transcription failed:` prefix and stops before emitting a reply event — so the question stays pending rather than getting a garbage answer. This is arguably correct-ish behavior already (fails safe, doesn't corrupt the answer) and is NOT in MILE-21's acceptance criteria — leave it alone, out of scope for this phase.
- Socket chmod TOCTOU race (`ipc-server.ts` listen()) — real but not in MILE-21 scope (no AC mentions socket permission races). Out of scope.

**Drifted / more nuanced than the audit doc claims — read the current code, not the doc, for these:**
- The audit doc's headline claim ("any tool call hangs ~45s because of the reconnect loop") is **not accurate for new tool calls**: `adapter/index.ts`'s `proxyTool()` already does `if (!ipcClient || !ipcClient.isConnected()) throw new Error(...)` — a synchronous, immediate throw. `IPCClient`'s socket `'close'` handler flips `this.connected = false` and rejects all pending requests immediately (`'IPC connection closed while request was pending'`) *before* emitting `'disconnected'`. So a NEW tool call issued while the daemon is down already fails fast today, and an IN-FLIGHT call also fails fast on daemon crash (no 45s wait). **The real, still-live bug is different and worse: the reconnect loop's exhaustion path calls `process.exit(1)` on the adapter process itself** after ~45s of failed exponential-backoff attempts — killing the whole MCP adapter with no typed/structured signal Claude Code or the calling agent can act on; it just looks like the MCP server vanished. That's the actual "daemon death is detected instead of silently hanging" gap to close, not a per-call hang.
- The audit's issue #3 ("question timeout race... adapter still waiting 30m") is also not quite right given current code — the adapter's pending IPC request already resolves via the socket `'close'` handler as soon as the daemon dies, well before any 30-minute window. **The real, still-live bug is in `restoreState()`:** a question that was pending (not yet answered, not yet expired) when the daemon crashed gets restored into the live `questions`/`threadToQuestion` maps with **no active `setTimeout` and no `once('answer:...')` listener** (both died with the crashed process — there is no way to resurrect an in-memory `Promise` across a process crash). That question becomes a permanent zombie: if the user later replies in its thread, `deliverAnswer()` finds the threadId mapping and calls `this.emit('answer:${questionId}', text)` into a void with zero listeners — the emit silently no-ops, the handler in `daemon/index.ts` still logs "delivered" and reacts with a checkmark (because `deliverAnswer()` returns `true` just for finding the threadId, not for having a real listener), and the "answer" is lost forever while the record sits in memory with no way to ever expire (nothing rechecks it unless the daemon crashes and restarts *again*). Only questions that are already-expired at restore time get the existing (correct) "notify + drop" treatment; non-expired restored questions get neither a timer nor a listener — they're simply never resolved.
- MILE-21's phrase "daemon crash during a pending question fails the question deterministically" is precisely a fix for this restoreState gap: EVERY restored pending question is orphaned by definition (the crash destroyed its owning Promise/listener no matter how much time was left on the clock) — so `restoreState()` should apply the same "notify the thread + do not restore into the live waiting maps" treatment to ALL pending questions it finds, not just the ones that happen to already be past their `timeoutMinutes` deadline. Collapsing the two paths (silent zombie vs. explicit stale-drop) into one deterministic "restored pending question = failed, always" path is the concrete 47-01 deliverable.

## Implementation Decisions

### Plan 47-01: Daemon-crash detection + double-timer race fix
- **Fix `QuestionService.restoreState()`** so every restored pending (unanswered) question is treated as orphaned and deterministically failed, regardless of whether its `timeoutMinutes` deadline has technically passed yet — not just the already-expired ones. Notify the original thread (reuse the existing stale-notification message pattern, but make the wording accurate for both "expired" and "not-yet-expired-but-orphaned" cases — e.g. distinguish "timed out while daemon was down" from "daemon restarted — this question cannot be resumed, please re-ask if still needed"). Do not add orphaned questions to `threadToQuestion` (so a stray reply in that old thread doesn't get silently swallowed as a phantom "delivered" answer with a listener count of zero) — a reply to an orphaned thread should log clearly at `warn`/`info` that it landed on a dead question, not report a false "delivered".
- **Add a typed/structured error signal for daemon-unavailable**, surfaced through the existing MCP tool error JSON shape (`{ error: errorMessage, tool: name }` in `adapter/index.ts`'s catch block) — e.g. add a stable `code: 'DAEMON_UNAVAILABLE'` field so a calling agent (or a future retry/fallback layer, see 47-03) can distinguish "daemon is down" from other tool failures programmatically instead of string-matching an error message.
- **Address the reconnect-loop's `process.exit(1)` silent-kill path** (`adapter/index.ts` `attemptReconnect`) — this is the actual "daemon death is detected instead of silently hanging" gap (see predecessor_state). At minimum: log loudly and distinctly (already partially done via `log.error`) with the typed code above before exiting, and make sure this path is unit-testable (extract the give-up decision into a small pure/testable unit rather than leaving it inline in a fire-and-forget async closure). Whether to keep the eventual `process.exit(1)` (simplest — MCP stdio servers are expected to be respawned by Claude Code / the daemon-launcher on the next tool call) or replace it with some other terminal signal is the planner/executor's call; the acceptance bar is "prompt typed error to the calling agent, not a silent ~45s reconnect hang" — a full 10-retry/45s exhaustion before ANY signal reaches the caller is itself the thing to shrink or make loud, since in practice the very next tool call already gets an immediate `DAEMON_UNAVAILABLE`-coded error today (per predecessor_state) — verify this experimentally with a real test (kill a test daemon mid-session, confirm the next tool call errors in milliseconds, not 45s) rather than assuming either the old audit doc or this analysis is exactly right.
- **Document + test single-timer ownership**: the daemon-side `question-service.ask()` internal `setTimeout` is the sole authority on "did the user answer in time." The adapter-side `IPCClient.methodTimeout()` value for `ask_blocking_question` (`(timeoutMinutes*60+60)*1000`, i.e. a 60-second buffer past the daemon's own deadline) is a dead-man's-switch backstop only, for the case where the daemon never responds at all (hard hang, not a clean crash-with-socket-close). Add a code comment making this ownership explicit at both call sites, and a test proving: (a) when the daemon's own timeout fires first, the IPC response carries the error and the adapter's backstop timer is cleared via the normal `handleLine()` path (already structurally true — confirm with a test, don't just assert it in prose); (b) when the daemon process dies outright, the adapter's pending promise rejects via the socket `'close'` handler, not via the 60-second backstop; (c) restored/orphaned questions (see restoreState fix above) never re-enter a state where a *third* copy of "the answer" is expected.

### Plan 47-02: JSONL state locking + delivery-failure retry
- **Atomic write-rename for `question-state.jsonl`**: change `saveState()` to write to a temp file in the same directory (`${stateFilePath}.tmp-${process.pid}-${random}`), then `fs.renameSync()` over the target — POSIX rename is atomic, so concurrent/crashing writers can never leave a torn/partial-line file for a reader to choke on. This satisfies the AC ("real file locking... or atomic write-rename") without introducing `proper-lockfile`'s own lock-file lifecycle management; document in the plan/summary why atomic-rename was chosen over the vendored `proper-lockfile` dependency (simplicity, no lock-file cleanup/staleness concerns, sufficient for the single-writer-per-process / multi-process-torn-write threat model described in the audit) so the verifier doesn't flag `proper-lockfile` remaining unused as a gap.
- **Per-project state file scoping is Claude's discretion** (see below) — a small, low-risk addition (reuse the same SHA1-hash pattern as `getSocketPath`) that would eliminate the cross-project collision scenario entirely rather than just making torn writes safe. Only change the *path*, never the JSONL *record format* — and remember this only takes effect for daemons started after the change (operational constraint).
- **Delivery-failure detection + bounded-backoff retry**: add a small retry helper (e.g. 3 attempts, exponential backoff — 500ms/1500ms/4000ms is a reasonable starting point, exact values are the planner's call) and wrap the actual Telegram API calls in `bot/index.ts` (`sendToGroup`, `sendToThread`, `createForumTopic` — the three functions that currently call `bot.telegram.*` with zero retry) with it. Log every retry attempt at `warn` (loud, visible) and the final exhausted-retries failure at `error` (never silently dropped), then rethrow so callers keep their existing "does this notification's success matter to the caller" semantics — `send_message`/`send_status_update` IPC handlers already propagate a thrown error as an IPC error response to the adapter (no `try/catch` around those `await sendToThread/sendToGroup` calls in `daemon/index.ts` today), while `question-service.ts`'s own best-effort notification call sites (posting the question body, timeout notice, answer confirmation) already catch-and-log — after this change those catches will be catching a "retries already exhausted, logged loudly" failure instead of a first-attempt failure, which is the point: no notification failure is silently dropped anymore, but a notification failure still never blocks the primary blocking-question flow from returning the user's actual answer.
- Do not add retry to `reactToMessage()` (cosmetic checkmark reaction, not a "notification" per the AC's own examples of `send_status_update`/escalation messages) unless the planner finds a cheap way to fold it in for free — not required.

### Plan 47-03: Overnight blocking-question timeout fallback + integration tests
- **Daemon-side**: `question-service.ask()`'s existing timeout branch already rejects with a clear `Error` and notifies the thread — no change needed there beyond whatever 47-01 does to restoreState/error typing. The daemon does not need to know about `DEFERRED.json` — that's a workflow-layer (Claude Code agent prompt) concern, not a daemon concern, since the daemon has no notion of "phases" or "plans."
- **Workflow-layer wiring (the actual deliverable for this plan)**: `agents/gsd-phase-coordinator.md`'s discuss-step escalation loop (`Escalate sensitive items via Telegram` block, Step A — the `mcp__telegram__ask_blocking_question` call, source repo path `agents/gsd-phase-coordinator.md` ~line 387) is the ONLY call site of `ask_blocking_question` anywhere in `agents/`, `workflows/`, or `commands/` (verified by grep on 2026-07-04 — re-verify with a fresh grep during execution in case this has changed since). `workflows/execute-roadmap.md` has NO blocking Telegram call sites — its Telegram usage is exclusively fire-and-forget `send_message`/`send_status_update` notifications (e.g. the phase-failure notification's "reply retry/skip/stop" text is advisory prose the human may or may not act on; the roadmap coordinator does not literally block waiting for that reply) — so there is nothing to wire a timeout-fallback into on the execute-roadmap.md side. Document this as a verified negative finding in the plan/summary (with the fresh grep output) so the verifier can confirm it deterministically rather than trusting this pre-analysis, rather than silently skipping "wire into execute-roadmap.md" as if it were forgotten.
- Wrap the `ask_blocking_question` call in `gsd-phase-coordinator.md`'s Step A with fallback handling: on any failure (IPC timeout, `DAEMON_UNAVAILABLE`-coded error from 47-01, or the daemon's own question-timeout bubbling back as an IPC error response) — apply the configurable fallback:
  1. Log the failure loudly (this is what satisfies "the escalation failure itself appears in the milestone audit" per the AC — the mechanism for that visibility is the same `deferred add` Telegram notification + `audit-milestone`'s existing DEFERRED.json table from Phase 45/46, not a new audit code path).
  2. Write a `DEFERRED.json` waiver via the existing, ONLY-sanctioned CLI: `node get-shit-done/bin/gsd-tools.js deferred add {phase} --step discuss --reason "Telegram escalation timed out/unavailable for: {question}" --approver timeout-fallback [--plan {plan}]` (schema confirmed at `get-shit-done/bin/gsd-tools.js` `cmdDeferredAdd`, ~line 5399 — do not invent a parallel waiver mechanism).
  3. Park the blocked gray-area item into the Claude's-Discretion bucket (treat it exactly like a non-sensitive discretion item) so `CONTEXT.md` still gets written and planning can proceed — never leave the phase hung waiting on a reply that may never come.
  4. Continue the loop for any remaining `sensitive_items` and then continue the phase lifecycle normally.
- **Same fallback for "daemon down at escalation time"** — the AC calls this out as a distinct case from "user just didn't reply in time," but the workflow-layer handling is identical (both surface as the `ask_blocking_question` call throwing/rejecting) — one code path, both cases covered, do not build two.
- **Configurability**: the fallback policy itself (write-waiver + park + continue) is the hardcoded default per the AC ("configurable fallback (default: ...)"); expose the escalation timeout minutes as an overridable value via `.planning/config.json` (mirroring the existing `model_profile` config pattern) rather than the hardcoded `timeout_minutes: 30` currently in the prompt — planner's call on the exact config key name (e.g. `telegram_escalation_timeout_minutes`).
- **Integration tests** (this plan's `tdd` deliverable, spans both TS and workflow layers):
  - telegram-mcp side: daemon down → `ask_blocking_question`-equivalent (call `QuestionService.ask()` or the IPC path with a disconnected socket) → prompt typed error, not a long hang.
  - telegram-mcp side: question timeout fires → the daemon-side promise rejects with the expected message; simulate a restart mid-pending-question and confirm the restored question is deterministically failed (this may already be covered by 47-01's own tests — do not duplicate, reference them).
  - telegram-mcp side: concurrent `saveState()` calls (simulate via rapid sequential calls or two `QuestionService` instances sharing a temp path) → resulting file is always valid, parseable JSONL, never torn.
  - telegram-mcp side: a wrapped Telegram send call that fails N times then succeeds → retried the expected number of times, eventual success returned; a call that fails all retries → logged loudly, error rethrown, not silently swallowed.
  - workflow layer: this is prose/agent-prompt logic, not TS — "integration test" here means a documented manual/scripted verification path (e.g. a small Node script or a documented walkthrough) proving that when `ask_blocking_question` throws, a `DEFERRED.json` entry with `approver: "timeout-fallback"` is actually written and picked up by `deferred list`/`audit-milestone` — the planner should decide the lightest-weight way to prove this deterministically (e.g. a `gsd-tools.js` test that directly exercises `cmdDeferredAdd` with `approver: 'timeout-fallback'` and confirms `deferred list` surfaces it, since the actual Telegram-calling prose can't be unit-tested the way TS code can).

### Test infrastructure decision (applies to all 3 plans)

Add a `"test": "node --experimental-strip-types --test 'src/**/*.test.ts'"` (or equivalent glob the shell/npm resolves correctly) script to `mcp-servers/telegram-mcp/package.json`. Per the task's predecessor context, root `npm test` covers `get-shit-done/bin/gsd-tools.test.js` etc. only — this phase's TS tests run via the telegram-mcp package's own `npm test`, invoked separately (`cd mcp-servers/telegram-mcp && npm test`) as part of each plan's pre-SUMMARY.md verification, per the task instructions ("check mcp-servers/telegram-mcp/package.json for its own build/test scripts and run those too").
