<objective>
Fix the two real, source-verified reliability gaps in the Telegram MCP daemon/adapter pair: (1) `QuestionService.restoreState()` orphans every restored pending question with no timer/listener, so a reply that arrives later is silently lost forever; (2) the adapter's reconnect-exhaustion path (`process.exit(1)`) kills the whole MCP server with no typed signal a calling agent can act on. Both are documented, source-verified in `47-CONTEXT.md`'s `<predecessor_state>` section -- read it before touching any code, it corrects a drifted prior audit doc.

Purpose: this is the escalation channel every other autonomy feature (debugger injection, Phase 48) routes through -- a daemon crash during a pending question must fail deterministically, and daemon death must surface as a typed error instantly, not a 45s silent hang.

Output: `restoreState()` treats every restored pending question as orphaned (deterministic fail, not silent zombie); a `DaemonUnavailableError` (code `DAEMON_UNAVAILABLE`) is surfaced through the MCP tool error JSON and used consistently at every client-side daemon-unavailability detection point; the reconnect give-up decision is extracted into a testable pure function; single-timer ownership between the daemon's `ask()` timeout and the adapter's IPC backstop is documented and proven by test.
</objective>

/** Pure decision logic for the adapter's reconnect-with-backoff loop. */
export function shouldGiveUpReconnecting(attempt: number, maxRetries: number): boolean {
  return attempt > maxRetries;
}

export function computeReconnectDelayMs(attempt: number, baseDelayMs: number, maxDelayMs: number): number {
  return Math.min(baseDelayMs * Math.pow(2, attempt - 1), maxDelayMs);
}
