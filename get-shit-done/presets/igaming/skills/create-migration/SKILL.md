# Create Migration Skill

## When to Use

This skill auto-invokes when plan tasks mention:
- Creating migrations, tables, columns, indexes
- Adding/modifying RLS policies or row level security
- Schema changes or database functions
- ALTER TABLE, CREATE TABLE operations

## Scaffolding Process

### Step 1: Generate Migration File

```bash
cd apps/api
supabase migration new <descriptive_name>
```

This creates a timestamped file: `apps/api/migrations/YYYYMMDDHHmmss_descriptive_name.sql`

**Naming rules:**
- Use snake_case for names
- Be specific: `add_player_sessions` not `update_tables`
- Timestamp auto-generated by Supabase CLI

### Step 2: Apply Template Structure

Every migration MUST have these sections:

```sql
-- ============================================================================
-- Migration: {DESCRIPTION}
-- Release: {RELEASE_TAG}
-- Created: {DATE}
-- Author: {AUTHOR}
-- ============================================================================

-- ============================================================================
-- ROLLBACK PLAN
-- ============================================================================
-- {rollback SQL or "Data-only change, no rollback needed"}

-- ============================================================================
-- RLS SECURITY CHECKLIST
-- ============================================================================
-- [x] All new tables have RLS enabled
-- [x] Appropriate policies created
-- [x] NULL checks in policies
-- [x] Service role policy included

-- ============================================================================
-- MIGRATION CONTENT
-- ============================================================================
-- {actual SQL}
```

### Step 3: Implement with RLS

**For tables in domain schemas (player, games_catalog, etc.):**

```sql
-- 1. Create table in domain schema
CREATE TABLE IF NOT EXISTS {schema}.{table_name} (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    player_account_id UUID NOT NULL REFERENCES player.player_accounts(id),
    -- columns...
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 2. Enable RLS (CRITICAL - never skip)
ALTER TABLE {schema}.{table_name} ENABLE ROW LEVEL SECURITY;

-- 3. Service role policy (required for admin operations)
CREATE POLICY "{table_name}_service_role"
    ON {schema}.{table_name}
    FOR ALL
    TO service_role
    USING (true);

-- 4. Player access policy (with NULL check)
CREATE POLICY "{table_name}_player_access"
    ON {schema}.{table_name}
    FOR SELECT
    TO authenticated
    USING (player_account_id = current_setting('app.current_user_id', true)::UUID);
```

**For tables needing public view access:**

```sql
-- 5. Create public view (PostgREST access)
CREATE OR REPLACE VIEW public.{table_name} AS
SELECT * FROM {schema}.{table_name};

-- 6. Enable security invoker on view
ALTER VIEW public.{table_name} SET (security_invoker = true);

-- 7. INSTEAD OF triggers for writes
CREATE OR REPLACE FUNCTION {schema}.handle_{table_name}_insert()
RETURNS TRIGGER AS $$
BEGIN
    INSERT INTO {schema}.{table_name} (...)
    VALUES (...);
    RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER {table_name}_insert_trigger
    INSTEAD OF INSERT ON public.{table_name}
    FOR EACH ROW EXECUTE FUNCTION {schema}.handle_{table_name}_insert();
```

### Step 4: Include Rollback Comments

**For infrastructure changes:**
```sql
-- ROLLBACK PLAN
-- DROP VIEW IF EXISTS public.{table_name};
-- DROP TABLE IF EXISTS {schema}.{table_name} CASCADE;
-- DROP FUNCTION IF EXISTS {schema}.handle_{table_name}_insert();
```

**For data-only changes:**
```sql
-- ROLLBACK PLAN
-- Data-only change (INSERT/UPDATE), no rollback needed.
```

## Validation

After scaffolding, run validation:

```bash
deno run --allow-read apps/api/tools/validate-migration.ts apps/api/migrations/YYYYMMDDHHmmss_name.sql
```

**Validation checks:**
- Migration header present (`-- Migration:`)
- Release tag present (`-- Release:`)
- RLS enabled on public schema tables
- Naming convention: `YYYYMMDDHHmmss_descriptive_name.sql`
- No template placeholders remaining

## Arguments

When invoking this skill, provide:
- `$TABLE_NAME`: Name of the table/feature
- `$SCHEMA`: Domain schema (player, games_catalog, configuration_management)
- `$COLUMNS`: Column definitions
- `$ACCESS_PATTERN`: Who needs access (player-owned, public-read, admin-only, service-only)

## Before Commit Checklist

- [ ] Migration tested with `supabase db push --local`
- [ ] RLS enabled on all tables
- [ ] NULL checks in all policies using `current_setting()` or `auth.uid()`
- [ ] Service role policy included
- [ ] Rollback plan documented
- [ ] Integration tests pass
- [ ] Validation script passes

## Common Patterns

### Pattern: Player-owned records
```sql
USING (player_account_id = current_setting('app.current_user_id', true)::UUID)
```

### Pattern: Admin-only access
```sql
USING (current_setting('app.current_user_role', TRUE) IN ('operator_admin', 'operator_super_admin'))
```

### Pattern: Public read, authenticated write
```sql
-- Read policy
CREATE POLICY "public_read" ON {table}
    FOR SELECT TO anon, authenticated
    USING (true);

-- Write policy
CREATE POLICY "authenticated_write" ON {table}
    FOR INSERT TO authenticated
    WITH CHECK (current_setting('app.current_user_id', true) IS NOT NULL);
```
