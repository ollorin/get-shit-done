# Rigour (`standard` | `spike`), risk-domain add-ons and the phase budget

A phase has one rigour level: `standard` (default, no ROADMAP line) or `spike`. `resolveRigour()` in `bin/rigour.js` resolves it; `init plan-phase` and `init execute-phase` emit `rigour`, `rigour_source` (`roadmap` | `default` | `rejected`), `spike_roots`, `rigour_rejected_reason`. There is no third level: depth for risky work is the add-ons column below. The init output also carries `rigour_notice` (a visible mismatch or unknown value, never authority).

```
### Phase 2: Short Name
**Rigour**: spike (OG2)
**Spike roots**: spike/, scripts/probes/
**Risk domains:** auth, uploads
```

**Decided once, printed always.** The newest APPROVED roadmap owner gate of the milestone is the single source of truth for spike phases and roots: `gsd-tools owner-gate request --kind roadmap --spike-phases N,M --spike-roots a,b`. new-milestone proposes rigour in the owner-gate summaries (OG1: prototype or `standard`; OG2: per phase the rigour, risk domains and budget). The ROADMAP `**Rigour**:` / `**Spike roots**:` lines are informational (the roadmapper writes them for readers); a mismatch with the gate prints `rigour_notice`. plan-phase and execute-phase print as their first line `Phase {N}: rigour {rigour} ({rigour_source}), risk domains: {names | none}, budget {wall} min / {dispatches} dispatches`, plus `rigour_rejected_reason` when the source is `rejected` and `rigour_notice` when set. Changing the spike phases of an already approved roadmap gate needs a new approval: repeat the request with `--revise`; the gate goes back to pending and blocks the roadmap until the owner approves it.

**Risk-domain add-ons** engage when the init field `risk_addons` is true, the one boolean every workflow and agent keys on: a `standard` phase whose `**Risk domains:**` line is not `none` (`phase_risk_domains`). The per-plan `high_risk` flag and path matching are gone: `quality assess-risk` only reports the spike containment violation. The line is mandatory in every ROADMAP phase section: a comma list of single tokens from the project's `risk_domains`, or `none`; trailing prose is ignored, unknown tokens print a notice, and `owner-gate request --kind roadmap` fails when a phase that is not complete lacks it (the message names the phases and the exact line to add); a complete phase without it is one notice. For an old roadmap without the line `init plan-phase` matches the configured names against the phase goal and requirements and prints a notice.

Spike-only rules (executor, retried parked phase, spike path, negative answers, answer table, guards G1-G5, promotion): `references/rigour-spike.md`; read it only when `rigour` is `spike`.

## What runs

| | `spike` | `standard` | add-ons on a risk domain |
|---|---|---|---|
| Purpose | throwaway feasibility: evidence, never product code | product work | product work on `risk_domains` / `ruling_topics` paths |
| Discuss / research | no discuss step; at most one research agent, and only when the phase has no `*-RESEARCH.md` | discuss when there is no CONTEXT; at most one research agent | same |
| Plans / tasks / lines per plan | 2 / 4 / 150 | 250 lines (a task that needs more than one executor dispatch is split) | same |
| Planner | `ruling_model` | `ruling_model` | `ruling_model` |
| Plan-check | 1 round, `checker_model`, Dimensions 1-7, 12, 15, 16 (traceability, every rigour); one revision, no re-check | cap 2 rounds, `checker_model`: round 1 full, round 2 delta | round 1 on `ruling_model` with the adversarial pass and `{plan}-VERDICT.md`; same cap |
| After the cap | proceed; leftovers listed | warnings become `A-` rows (`cheap`); remaining blockers get ONE planner revision and ONE targeted re-check of only those blockers (same checker tier, delta scope) | same, then a blocker that survives goes to ONE ruling on `ruling_model` before execution, never an OVERRIDE line alone |
| Tests | none: one capture file per question | `<acceptance>` rows on the behaviour task; test steward once per phase | + T0: real-system test with one named mutant per behaviour, rows in SUMMARY `## Test Delta` |
| Extra artifacts | `SPIKE-RESULT.md` (last spike phase) | none | ONE `{N}-THREAT-MODEL.md` per phase (abuse case + control, written by the planner before execution) |
| Final phase review (verifier, `ruling_model`) | the only review: no secret in a committed file or capture, every written path inside the spike roots or `.planning/`, each capture matches its command and is newer than the code it ran, every question answered yes/no/inconclusive. A disproved hypothesis is `passed`. Its `{N}-VERIFICATION.md` is the review record | ONE pass: product truths, wiring, test run, gates; writes `{N}-REVIEW.md` and `{N}-VERIFICATION.md` | TWO sequential passes with the fix between them (rules 10, 12), + server-side authz read from the code, against the threat model |
| Ruling triggers | an effect that is irreversible outside the spike roots; an open CRITICAL/HIGH after the fix dispatch | irreversible, or legally or financially material | + a design choice, an accepted plan deviation or a loosened assertion on the risk-domain path |
| Gap closure / findings of the final review | rule 12; at `breach` all of it still runs, counted in the dispatch budget. The coordinator logs a `spike_ruling` event when it spawns the ruling; if the phase returns without, `roadmap record` answers `ruling` and the roadmap orchestrator only re-enters the phase coordinator for it. A ruling counts only after the phase's latest `phase_start`. A non-CRITICAL/HIGH finding that was not mechanical stays listed as open in `SPIKE-RESULT.md` and the VERIFICATION body. A question still open is `inconclusive` | rule 12; light path for at most 4 small fixes; re-verify only what failed | rule 12; one full cycle; re-verify only what failed |
| Budget, wall minutes | 45 min | 90 min | 150 min for the phase |

Not produced unless a cell says so: an E2E plan without UI, a threat model, mutants, a per-plan copy of a phase document, an evidence-only plan, an index or registry, findings copied between files.

## Rules for every phase

1. **Form is a script; the final review judges product truth.** Plan-time: the planner runs `gsd-tools verify form {N} --plans-only` (plan line cap, and at spike the plan and task counts, over UNEXECUTED plans; evidence-only plan, missing `plan_stamp`) and fixes every error before plan-check; executed plans (with a SUMMARY) are never checked for caps. After execution `gsd-tools verify phase-gate {N} --pre-verifier` returns `failures` (missing WORK, including `missing_evidence`), `work_errors` and `form_errors` (SUMMARY Self-Check section missing; a planning-record line cite in a PLAN or SUMMARY the phase wrote; ledger rows are never checked). Form is `form_errors` only; never use `evidence_errors` or `work_errors` to decide form. Form errors get no fix dispatch (plan caps are plan-time only): they are closed with `gsd-tools phase complete {N} --form-debt` (recorded in VERIFICATION frontmatter `form_debt`); it still refuses on missing work. A form debt never parks, never becomes `gaps_found`, never blocks dependents, and is never ruled on. A form issue the verifier notices goes in its report body and changes no status.
2. **Ids, not lines, for planning records.** Cite `D-34`, `A-25`, a requirement id, `Phase 2`, plan `02-01`, a task number. `DECISIONS.md:<line>` and `ROADMAP.md:<line>` are never written (a render moves them); to quote a record, quote its text. Code cites stay `file:line`.
3. **Evidence is a capture file**: the command and its output under `{phase_dir}/captures/`, written by the task that built the behaviour. SUMMARY names the path and restates no counts or hashes, so a fix round has nothing to re-reconcile.
4. **Plan-check converges.** Round 2 receives the round-1 issue list and `git diff` of the plans (the checker's own round-1 fixes included) and answers two things: is each earlier finding closed, did a changed line break something. A new finding on unchanged text is a warning. Text a revision introduces is covered by that delta read and the final review, not re-attacked by the top model.
5. **Rulings only on the trigger row.** Anything else (a count, a literal, a name, a cleanup choice, wording) takes the stated default and one `A-` row logged `cheap`, with no dispatch. A ruling is one dispatch for all open items of a step.
6. **Plan size.** The line cap is checked at plan time, before the checker, by `verify form {N} --plans-only` (spike: also its plan and task counts). Standard has no plan or task count cap: a task that cannot be done in one executor dispatch (roughly more than ~5 files or two unrelated behaviours) is split by the planner, and a checker blocker otherwise. Size is also a limit: a task that enumerates many items (more than ~40 rows, sites or files) is split by a natural key (schema, directory, module) into tasks that each write their own part of the result, and writing a change and proving it (resets, mutants, rollback proof) are separate tasks when the proofs need more than a few commands. Weight: one named mutant per risk-domain behaviour, run once with no green re-run after it, and at most one whole-plan acceptance run per plan. A phase too big to plan is said so in the planner's return.
7. **Budget.** Defaults are the last table row; `workflow.budget.<spike|standard|risk>.wall_minutes` in config overrides (init field `budget_wall_minutes`). Dispatches are counted (`dispatches_spent`) but never limited: the plan-check cap bounds them and `warn`/`breach` use wall minutes alone. The coordinator calls `gsd-tools budget spend --phase {N}` once when it spawns any child agent (one dispatch), and `gsd-tools budget status --phase {N}` (`wall_minutes_spent`, `dispatches_spent`, `pct`, `warn`, `breach`) before each NEW cycle (plan-check round, gap cycle). Wall time is the sum of work windows (phase start, or the first spend event when the phase has none, to the next record, park or complete, measured to the phase's last logged event, never the clock); idle time between sessions never counts. **At `warn` (80 %):** finish the step in progress and start no optional work (no re-check beyond rule 12, light-path gap cycle or second research). Mandatory steps still run: the final review and `phase complete`.
   **At `breach` (100 %):** start no new cycle or scope (plan-check round, gap cycle, retry, unstarted plan) and let the running child finish. When every plan has a SUMMARY the final review still runs, on `ruling_model` (two sequential passes at risk add-ons), and so do rule 12's fix dispatch (mandatory when a CRITICAL/HIGH is open), the fix re-check and the one ruling for what the re-check left open: none is ever skipped for budget, and a finding of lower severity is fixed in that dispatch or becomes an `A-` row (rule 12), never left open silently; the breach stops everything after them. Then: the final review ran, `{N}-VERIFICATION.md` is `passed` and nothing mandatory was skipped: the phase completes and the breach is recorded in its `phase_complete` event; anything else: print an owner report of at most 15 lines naming each skipped step and each open finding and return `status: blocked`, `reason: budget_exceeded`.
   **Never silent.** A mandatory independent check that did not run (the final review) means the phase is not complete: `phase complete` refuses without a passed `{N}-VERIFICATION.md` (and, above spike, a `{N}-REVIEW.md`), and the coordinator never reports `completed` over a skipped check.
   When `phase complete` is recorded (`roadmap record`), its `phase_complete` event carries `wall_minutes_spent`, `dispatches_spent`, the budget and `breach`; `budget status --phase {N}` on a completed phase returns those recorded numbers (`final: true`).

8. **Top model.** `ruling_model` and `ruling_model_fallback` are the configured top model; `references/models.md` says where they come from and who always uses them. No other file names a model for those roles.
9. **Plan stamp.** The planner copies `plan_stamp` from an `init plan-phase` call made immediately before the planner spawn into each PLAN frontmatter (hash of the ROADMAP phase section, the phase's requirement lines, CONTEXT and RESEARCH; no ledger rows: what a plan depends on is in CONTEXT). `plans_stale: true` is consumed once, in plan-phase.md; never re-plan on a guess.

10. **The final review is a disk check.** The phase's independent review is the final pass on `ruling_model`, merged with verification: ONE dispatch reads the phase diff (`git diff {phase base}..HEAD -- . ':!.planning'`; `{phase base}` is the `phase_base` field of `init execute-phase`: the parent of the phase's oldest commit, matched as rule 12's Freshness says), the plans, the threat model when present, `captures/gates.txt` and the test steward's return, and writes its findings and `{N}-VERIFICATION.md`. At risk add-ons there are TWO sequential passes: pass 1, the fix of rule 12, then pass 2, a fresh `ruling_model` agent on the fixed tree with a DIFFERENT brief (pass 1 is the plan-and-diff pass of rule 11; two diff-vs-plan passes share one blind spot): it does not start from the plan; for each actor, role or caller it states what they can still do or reach after the change and what the phase goal says they must not, measures it itself where it can run something (a query, the phase's tests, a probe), and reports the residual surface: capabilities left open, things the plan excluded or ruled out without a compensating control, and sibling sites of a defect class the phase recorded but did not fix. It is NOT given pass 1's findings as things to look for; it gets pass 1's finding ids and the fix commits only to judge each closed / still open and whether a fix introduced a new defect, and it still runs when pass 1 found nothing. The record is `{N}-REVIEW.md` (the newest pass overwrites it) with frontmatter `passes` (1; 2 at risk add-ons, written by pass 2), `open_critical_high` (count still open) and, after a ruling, `ruled_by: [D-NN]`, then one line per finding (id, severity, `file:line`, `scriptable`, what, fix; at pass 2 also each pass-1 id closed / open). `verify phase-gate` and `phase complete` report missing work when a phase that changed files outside `.planning/` (a spike is exempt: its VERIFICATION file is the review record) has no `{N}-REVIEW.md`, records fewer passes than its risk add-ons need, or has open CRITICAL/HIGH and no ruling id (`bin/review-gate.js`; the pre-verifier gate does not require it). VERIFICATION's `open_critical_high` equals the record's.

11. **Question traceability, negative answers, final-review questions (every rigour; stated once here, role files point to it).**
   - **Traceability (plan time).** The planner lists, per question / success criterion, its source requirement AND the source PRD's exit or acceptance criteria it comes from (path + heading or id), and every source criterion the plan does NOT cover with a reason. The plan-checker's single round opens the PRD and verifies that list; an uncovered criterion without a stated out-of-scope reason is a blocker. Every success criterion AND every named deliverable in the phase's roadmap entry maps to a task (cite its id) or to a decision id that drops or defers it with the reason; a criterion that asks for a ruling or decision maps to a task that produces the decision record, not only to code; the plan-checker fails an unmapped one.
   - **Negative answers (spike):** see `references/rigour-spike.md`.
   - **Final-review questions and brief (top model; pass 1 of rule 10 answers all of it; pass 2 takes the brief of rule 10 and answers (vi)-(ix) only).** A finding is a way the product misbehaves or a test that cannot catch a break; wording, record form, comment style and naming are not findings. A risk-domain path is any path the product brief lists under Risk Domains (`risk_domains` in init; authentication/authorisation and security always; with `risk_domains_source` `builtin`, every path that mutates state). Rate no risk-domain or authz finding below HIGH unless the trace shows no reachable path, and enumerate what public or unauthenticated routes expose, including code outside the diff. `gsd-tools verify test-content <phase>` MISSING or hollow is a finding. A RED that fails on a TypeError, import error or timeout instead of the named defect does not count. For every conclusion or recommendation: (i) does each reason against the rejected option apply ONLY to it, or equally to the chosen one; (ii) could the probe or test have produced the opposite result; (iii) are conditions joined correctly (and / or); (iv) was the chosen option proven to the same standard as the rejected one. For each changed code path, each item yields a finding or "none, because <file:line>": (v) the project rules and their concrete instance here; (vi) privileges: every new endpoint or handler applies authorization server-side, an unauthorized caller is rejected by a test, and no authority (role, owner, id) is taken from the request; (vii) ignored results, and the state left when a dependency read fails, returns zero rows or many; (viii) failure class: an infrastructure failure reported as a permanent refusal, a refusal reported as success; (ix) guard coverage: unknown values, variants, other roles; every new enum, status or type value exists in every layer that must know it (store constraint, validation, handler, client type, display map); (x) tests: a reachable failing assertion, not status-only where a body or state effect is the behaviour; each refusal case reaches the branch it names; a positive control; shared state (what an install or probe changed that a product would inherit). (xi) for each new or changed test name the code change it would NOT catch; a finding when that change is plausible; (xii) sweep readers, callers and siblings OUTSIDE the diff of every changed behaviour with the profile's `search` command; (xiii) duplication and layering: a constant or helper copied from elsewhere, logic in the wrong layer per the project's rules. A check you cannot run is "unverified" with the mutation that would settle it, never an asserted result. Cite `file:line` as the line number in the file on disk, never a diff position. The pass MAY run a single test file, or apply a plan's named mutant in a throwaway worktree, to confirm a suspicion; it never re-runs the full suite. Each finding carries `scriptable: yes|no` (yes: a lint, grep or schema check could catch the class mechanically); the phase report lists the `yes` ones as proposed project gates (a list for the owner, no machinery). At spike: (xiv) how many of the phase's exit criteria (traced at plan time) have a decided pass or fail: the verifier writes `criteria_decided: <n>/<m>`, and with n = 0 the result headline is "undecided: next probes ..." (frontmatter `headline: undecided`), with no recommendation or default; a recommendation cites the decided criteria it rests on. The review writes frontmatter `open_critical_high` and, after a ruling, `ruled_by: [D-NN]` into `{N}-VERIFICATION.md`; `verify phase-gate` and `phase complete` refuse while it lists an open CRITICAL/HIGH with no ruling id (`bin/review-gate.js`, `verificationReviewErrors`).

12. **After a final pass (every rigour; stated once; the only statement of who fixes, how many dispatches and what is rerun).**
   - **Fix.** ONE fix dispatch for the record's findings of every severity, mandatory when a CRITICAL/HIGH is open: `gsd-executor` on `executor_model` with `references/executor-task.md`, the findings as its task list, commits tagged `fix({N}-review)`; never parallel fix executors (rule "Never relaxed" 6). Its brief carries every numbered fix and bounded probe verbatim and its report gives each a status (done with commit or capture path, or not done with reason). It then re-runs every `stack.gates` entry and the test files the fix touched (and their bucket); the coordinator appends command, rc and output to `captures/gates.txt` (the full test run is not repeated). The only deferral is a finding with no business value: a reason and an `A-` row (never for a CRITICAL/HIGH).
   - **Freshness (one notion).** A phase record (`captures/gates.txt`, `{N}-VERIFICATION.md`, `{N}-REVIEW.md`) is stale when the phase has a later commit that changes a source path (not under `.planning/`, not under `docs/`); docs-only commits never stale it. "The phase's commits" have ONE matcher, `phaseCommits` (`bin/review-gate.js`), shared by the gate's commit check, touched files and `has_ui`, `phase_base` and `lastSourceCommitTs`: reachable from HEAD, the subject scope starts `({N}-` followed by `[0-9a-z]` (`({N}-NN)`, `({N}-review-r2)`, `chore({N}-gates)`, `test({N}-steward)`), the phase a whole token (`1` equals `01`, `36` is not `365`); never the body. A mechanical-gates fix and a ruling-condition commit use `fix({N}-review)`. Commits without an accepted tag fail the gate and `phase_base`, naming the form. `verify phase-gate` and `phase complete` refuse a stale VERIFICATION or REVIEW (`bin/review-gate.js` `staleRecordErrors`); the verifier fails a stale `gates.txt`.
   - **Re-check.** At risk add-ons, pass 1's fix is followed by pass 2 (rule 10), which is itself the check of those fixes; the re-check runs only after the fix dispatch that follows the last pass (none when the last pass has no findings). It is ONE `reviewer_model` `general-purpose` dispatch that reads only the fix commits (and the probes' captures) against the findings and reports per finding closed / still open; it re-traces the `file:line` cites in the phase records (including `{N}-REVIEW.md` and `{N}-VERIFICATION.md`) for every file the fix commits changed. The SAME agent then rewrites `{N}-REVIEW.md`'s `open_critical_high` and VERIFICATION's `open_critical_high` and `status` to the closed-finding result, records `fixed_by` (fix commit sha, re-run rc) next to each closed finding, and commits both after the fix: `status: passed` only when no truth is failing and no CRITICAL/HIGH is open without a ruling. A status is never edited by hand. A failed truth that is also a finding goes through this rule only; it goes to a gap cycle (`/gsd:plan-phase --gaps`) only when the re-check leaves it open.
   - **Ruling.** What stays open at CRITICAL/HIGH goes to ONE ruling on `ruling_model` that records `ruled_by` (then the re-check agent's counts and the ruling's are in step). A ruling that accepts a success criterion as not met names the compensating control and the test or guard that pins it, or states "none, accepted" with the residual risk in one line. Each condition a ruling imposes names the file that must carry it, and the coordinator checks the text landed there before recording `ruled_by`.

## Never relaxed

1. No secret in a committed file, capture or command output; captures are scanned.
2. No push, deploy or remote mutation by a spike beyond a throwaway target named in its authorisation. Hooks and guardrails are untouched.
3. No real user data and no production credentials in a spike.
4. A spike writes nothing outside its roots and `.planning/`.
5. Spike output is never promoted: no `standard` plan lists a spike-root path in `files_modified`, imports from it or cites spike evidence as a test REUSE.
6. One executor at a time per phase; owner gates OG1-OG3; the decisions ledger records every assumption.
